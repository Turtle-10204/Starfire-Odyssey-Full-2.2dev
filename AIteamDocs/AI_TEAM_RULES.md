# AI_TEAM_RULES --- Starfire Odyssey

## 合作模式

採用「平常專業分工、重大更新共同審查」的混合制。使用者是遊戲總製作人與最終決策者。

## 目前共同事實來源

1.  GitHub 上的 **2.11 拆檔版** 是目前唯一程式碼基準。2.1 單檔版倉庫僅供歷史對照，不再修改。
2.  2.11 是「純拆檔」版本：由原本約 6,916 行的 `sketch.js` 依功能拆成 19 個檔案，**邏輯未改動**，使用者已實機測試功能保留、無新增 Bug。
3.  `README.md` 描述技術架構與檔案結構；`PROJECT_CONTEXT.md` 描述版本與需求；`GAME_DESIGN.md` 描述遊戲規格；`BUG_TRACKER.md` 記錄問題；`CHANGELOG.md` 記錄已完成變更；`HANDOFF.md` 記錄交接與檔案鎖。
4.  README 若仍有單檔版行號，一律視為過期；以最新程式碼搜尋函式名稱確認。

## 程式架構速覽（2.11）

-   傳統 `<script>` 載入、共用全域作用域，沒有 ES Modules。
-   載入順序（定義於 `index.html`）：`world_maps.js` → `config.js` → `state.js` → `assets.js` → `audio.js` → `maps_world1.js` → `level_tiles.js` → `entities.js` → `player.js` → `boss_castle.js` → `world2_miner.js` → `world2_sandworm.js` → `world2_atmosphere.js` → `ui_hud.js` → `ui_modals.js` → `ui_screens.js` → `ui_worldmap.js` → `input.js` → `level_flow.js` → **`sketch.js`（永遠最後）**。
-   函式可跨檔案互相呼叫（執行期才解析）；順序只影響檔案最上層 `let`/`const` 的初始化。

### 模組歸屬

| 檔案 | 負責內容 |
|---|---|
| `config.js` | 常數：影格數、碰撞盒、`TILE_SIZE`、道具圖鑑文字 |
| `state.js` | 核心共用狀態（主角物理、遊戲流程、實體陣列、計時器） |
| `assets.js` / `audio.js` | 素材載入與材質／音效與 BGM |
| `maps_world1.js` / `world_maps.js` | 世界 1 地圖與 `loadLevelMap`／世界 2 地圖生成器 |
| `level_tiles.js` | 碰撞、磚塊、水管、旗桿、移動平台、地圖繪製 |
| `entities.js` | 敵人、道具、金幣、浮動文字 |
| `player.js` | 受傷／死亡、時光倒流、火球、仙人掌飛針 |
| `boss_castle.js` | 1-4 魔王城 |
| `world2_miner.js` / `world2_sandworm.js` / `world2_atmosphere.js` | 2-4 礦坑／2-5 巨蟲與救援過場／世界 2 氣氛 |
| `ui_hud.js` `ui_modals.js` `ui_screens.js` `ui_worldmap.js` | HUD／彈窗／全螢幕畫面／大地圖 |
| `input.js` | 鍵盤、觸控、虛擬按鍵、點擊分派 |
| `level_flow.js` | `startLevel`、退出關卡還原 |
| `sketch.js` | `setup()` 與 `draw()` 主迴圈（約 1,260 行的 `draw()` 是最高風險區） |

### 高風險共用區（修改前必須先經 Claude 審查）

-   `state.js`、`config.js`：全專案共用，改名或改初始值會牽動所有模組。
-   `sketch.js` 的 `draw()`：狀態機、物理、動畫、繪圖全混在一起。
-   `level_tiles.js` 的 `checkCollision()`：只回傳有無碰撞、不分方向，沒有單向平台概念。
-   `input.js` 的 `handlePointerTap()` 與 `keyPressed()`：UI 點擊與按鍵分派。
-   `index.html`：載入順序。

## AI 職責

### Gemini --- 主要實作者

-   依已批准需求負責主要程式實作與整合。
-   修改前確認最新 GitHub 版本、目標檔案與相關函式。
-   每次交付列出修改檔案、函式、行為變更、風險與測試方式。

### Claude --- 程式碼審查員

-   檢查架構、跨檔案依賴、潛在 Bug 與回歸風險。
-   提供具體證據：檔案、函式、程式碼區段。
-   未經要求，不直接重寫整個模組或 `draw()`。
-   靜態檢查不等於實機測試，會明確標示。

### DeepSeek --- 技術研究員

-   提供替代演算法、邏輯分析與方案比較。
-   說明各方案的優缺點、複雜度與副作用。
-   未讀取程式碼前，不可把推論說成已確認的程式事實。

### ChatGPT --- 規格整理與 QA 顧問

-   協助整理需求、測試案例、遊戲平衡與審查意見。
-   比較不同 AI 的方案，指出衝突與未解問題。
-   不宣稱已完成未實際執行的瀏覽器或裝置測試。

### 使用者 --- 遊戲總製作人

-   決定需求優先順序、採納方案與批准修改。
-   負責實際遊玩與裝置測試，回報結果。
-   對正式版本與合併結果作最終確認。

## 修改規則

1.  **單一修改者（以檔案為單位）：** 同一時間只指定一個 AI 修改同一個檔案。不同檔案可由不同 AI 同時修改，但前提是兩者沒有互相依賴；只要涉及共用函式、共用全域變數或上述高風險共用區，就改為依序進行。
2.  **2.11 優先：** 以 2.11 拆檔版為基準，不引用 2.1 單檔版的行號或結構。
3.  **先讀後改：** 先讀本文件組與目標檔案的最新程式碼，再提出修改。
4.  **不猜測程式結構：** 未看到程式碼前，不可捏造函式、變數、行號或檔案內容。
5.  **保留架構：** 未經批准，不改成 ES Modules、打包工具，也不合併或重新切分檔案。
6.  **最小修改：** 優先小範圍、可回退的修改，不順手重構無關功能。
7.  **新增全域變數與檔案：** 只供單一模組使用的變數放在該模組檔案開頭；跨模組共用的放 `state.js`；常數放 `config.js`。新增檔案時，必須同步更新 `index.html` 的載入順序與 `README.md` 的檔案結構，並確認 `sketch.js` 仍在最後。
8.  **改名前先全專案搜尋：** 全域函式與變數是跨檔案共用的。重新命名、刪除或改變參數前，先搜尋所有檔案中的使用處。
9.  **碰撞與狀態機需追蹤呼叫點：** 修改 `checkCollision()`、`draw()`、`gameState` 或輸入分派前，先搜尋所有相關呼叫與依賴。新增或改名 `gameState` 時，要檢查 `draw()` 內所有 `if (gameState === ...)`、`keyPressed`、`handlePointerTap`。
10. **關卡識別要分世界：** 不可只用 `currentLevel === 4` 判斷世界 1 魔王城或世界 2 礦坑，需同時檢查 `currentWorld`。
11. **交付方式（使用者以手機／網頁編輯 GitHub 時）：** 檔案不大時交付「整個檔案」；較大的檔案（例如 `sketch.js`）交付「整個目標函式的替換版本」，並標明檔名、函式名稱與替換範圍。不要只貼片段而不說明位置。
12. **備份與版本控制：** 修改前建立 Git 分支或備份（可在 GitHub 網頁操作）；整合前檢查差異；`main` 保持可玩的穩定版本。
13. **不冒稱測試：** 靜態檢查、推理、瀏覽器測試與真實裝置測試要分開標示。
14. **使用者批准：** 重大設計變更、數值調整或架構遷移，先提出方案等待使用者批准。

## 協作交接與撞檔處理

AI 之間無法直接溝通，使用者是唯一的傳遞者。為了讓使用者的負擔最小，統一用 `HANDOFF.md`。

### 交接流程

1.  **派工前**：使用者在 `HANDOFF.md` 的「檔案鎖」登記修改者與檔案，並把 `HANDOFF.md`（檔案鎖＋最近 3 筆交接）與目標檔案目前版本一起交給該 AI。
2.  **交付時**：修改者除了「每次交付格式」之外，必須附上「交接摘要」（格式在 `HANDOFF.md`），由使用者貼進交接紀錄。
3.  **審查時**：審查者只看使用者給的差異或最新檔案，不憑記憶或舊版本回覆。
4.  **上傳後**：使用者清除檔案鎖，並記下 commit 代號。

### 預防撞檔

-   任何修改都必須標明「基準 commit」。若基準與目前 GitHub 最新版不同，該修改視為過期，必須先重讀最新檔案再重做。
-   開工前先看「檔案鎖」；被鎖定的檔案只能審查，不能修改。
-   高風險共用區一律依序進行，不同時修改。
-   同時進行的任務必須是不同檔案，且彼此沒有共用函式或共用變數的依賴。不確定時視為有依賴，改為依序進行。

### 撞檔時怎麼處理

若兩位 AI 仍然基於同一個基準修改了同一個檔案：

1.  **不要擇一直接覆蓋，也不要兩份都貼進 GitHub。**
2.  使用者把「基準版本」與「兩份修改後的函式或檔案」一起交給審查者（Claude），請他列出：兩邊各改了什麼、有沒有改到同一函式、是否互相衝突。
3.  由原本被指定的實作者（預設為 Gemini）依審查結果產出一份「整合版」，其他 AI 不再各自修改。
4.  整合版經審查者檢查後，由使用者實測，通過再上傳並更新 `HANDOFF.md` 與 `CHANGELOG.md`。

## 重大更新審查流程

1.  使用者提出需求與驗收條件。
2.  Gemini 提出實作方案與影響檔案、函式。
3.  Claude 審查架構、邊界條件與回歸風險（高風險共用區為必審）。
4.  DeepSeek 提供替代方案或演算法分析。
5.  ChatGPT 整理 QA 案例、平衡性與意見衝突。
6.  使用者選定方案。
7.  指定一個 AI 實作。
8.  其他 AI 審查差異，不平行覆寫同一檔案。
9.  使用者或指定測試者實際測試。
10. 通過後更新 `CHANGELOG.md`、`BUG_TRACKER.md` 與必要的專案文件。
